# dugite v2.0.8

Byte-exactness + liveness release. Resolves the v2.0.7 backlog's restart-wedge
liveness blocker (#762) and the Conway PlutusV3 budget-exhausted divergence
(#764), plus the first half of the Conway PlutusV3 ScriptContext data-shape
divergence (#761). Each ledger/consensus change is cross-checked against the
canonical IntersectMBO/cardano-ledger source via the cardano-ledger / Haskell
oracle and pinned to a real on-chain transaction with a regression test.

## Fixes

- **#762 — Restart wedge under slow ValidateAll sync** (`95bb52514b`). Three
  layers: (1) the post-replay `publish_ledger_view` sent the LEDGER tip, which
  after a partial replay (chunk files that don't connect, or an LSM
  fork-rollback) is BELOW the ChainDB tip — regressing the #742 startup seed and
  parking every incoming header on the stale lower tip → permanent wedge in
  genesis bulk-sync (self-heals only on a 2nd restart). The tip watch is now
  re-seeded to the ChainDB tip after replay (the forecast gate is admission-only;
  apply-time validation + the genesis LoE stay authoritative). (2) The `biased`
  main `select!` kept the fetched-block arm ahead of the `maintenance_ticker`, so
  under sustained ValidateAll the volatile→immutable flush never ran and the
  VolatileDB grew to ~259k blocks / ~12 epochs, stranding every snapshot above
  the immutable tip. The flush is now forced every 256 blocks, bounding the
  VolatileDB within ~k. (3) `prune_old_snapshots_in_dir` now spares the newest
  snapshot at-or-below the ImmutableDB tip, guaranteeing a restart-recoverable
  anchor. Matches Haskell ouroboros-consensus (`copyToImmutableDB` runs
  unconditionally; snapshots are taken for immutable states). Regression tests
  for the prune floor guard.

- **#764 — Conway PlutusV3 budget-exhausted divergence** (`466ca2c889`,
  `3e65ef89cf`). At the Babbage→Conway hard fork `on_era_transition` seeds the V3
  cost model from the Conway genesis, but `process_epoch_transition` then applies
  any pending pre-Conway (Babbage) PPUP, which wholesale-replaces `cost_models`
  (mainnet ep506 has two quorum-meeting PPUPs carrying `{PlutusV1,PlutusV2}`),
  wiping V3. With `plutus_v3 = None` for the Conway era, every PlutusV3 phase-2
  eval fell back to the DEFAULT cost model — `equalsByteString` over-charges vs
  the real on-chain model (the constant ~1453-cpu overrun, `cpu_remaining=14547`).
  Fixed by re-seeding V3 after the PPUP apply (Haskell's PPUP-then-`translateEra`
  order; `Map.union {V3_genesis} {V1,V2}`). Proven that `apply_v3` is byte-exact
  vs the real model, so the over-count was purely the DEFAULT fallback. Regression
  tests for both the re-seed and the DEFAULT-vs-real over-charge.

- **#761 (Bug 1) — Conway ParameterChange `ChangedParameters` encoding**
  (`dc63e8b140`). The V3 `ChangedParameters` field was a hardcoded placeholder
  (`Constr 0 []`), so the Conway guardrails scripts that `unMapData` it failed
  (`unMapData on non-Map Data`; mainnet txs 51f495aa, b2a591ac — both propose the
  ep526 297-entry PlutusV3 cost-model change). Now encoded as
  `Data::Map [(I ppuTag, value)]` keyed by the Conway `ppuTag` integer, matching
  cardano-ledger `ToPlutusData (PParamsUpdate)` (oracle-verified mapping + value
  encodings: rationals as `List[num,den]`, CostModels as `Map[(I lang, List)]`,
  ExUnits/Prices, voting-threshold lists). Regression tests pinned to tx 51f495aa.

## Known-open / under investigation

- **#761 (Bug 2)** — A separate class of rare V3 SPEND txs (71579b77, e998e761)
  fails phase-2 with `appendByteString: expected ByteString, got Builtin`. All 16
  V3 TxInfo fields verified structurally correct; the diverging value requires a
  runtime applied-flat-term dump (`DUGITE_DUMP_APPLIED_DIR`) to pinpoint. The node
  trusts on-chain consensus and applies the block, so ledger state stays correct.
  #761 remains OPEN for Bug 2.

- **#763 — Reserves divergence (ep524+).** Localized to small, BIDIRECTIONAL
  per-pool GO-snapshot stake deltas (largest pool −632K ADA, another +6K) — not a
  uniform inflation and not a reward-formula bug (formulas re-verified correct;
  the prior agent's "missing appPerf cap" lead was refuted via the era-rules).
  Determined to be **inherited reward-account drift carried in `db-mainnet-val`**
  from old binaries (the ep388 ~996K-ADA injection), faithfully propagated by the
  byte-exact current code. No current-code fix shipped (a speculative change would
  itself diverge). The decisive confirmation is a clean from-genesis mainnet sync;
  #763 remains OPEN pending that soak. See
  `reports/issue-763-investigation-2026-06-15.md`.
