## #805 — UtxoStore swallowed LSM read errors (`crates/dugite-ledger/src/utxo_store.rs`)

Policy: crash-don't-diverge, matching the pre-existing `insert`/`delete` panic policy. A read `Err` mapped to `None` in `lookup`/`remove`/`contains` looks identical to "not found" to the caller — for `remove` that skips the tombstone write (resurrects a spent UTxO on the next lookup); for `contains`/`apply_transaction`/`apply_block_batch` it mislabels a real I/O fault as `InputNotFound`.

Fixed 6 call sites, each splitting `Ok(None)` (return normally) from `Err(e)` (panic): `lookup` (was `warn!`+`None`, now panics — this is why `warn` needed staying in the `tracing` import for #806's `scan_all`), `remove` (the `_ => return None` catch-all), `contains` (`matches!` → explicit `match`), `apply_transaction`'s replay-mode existence check, `apply_block_batch`'s pass-1 existence check. `scan_all`'s decode-drop is explicitly OUT of #805 (owned by #806).

**Test technique worth remembering**: `UtxoStore` wraps a concrete `dugite_lsm::LsmTree` directly (no trait indirection), and `dugite-lsm` has zero fault-injection seams. To get a REAL `Err` out of `LsmTree::get` in a unit test: open with `open_with_config(path, 0, ..)` — `memtable_size_mb=0` forces `LsmTree::insert` to flush to disk after every single insert (`approx_bytes() >= 0` is true as soon as the memtable is non-empty) — then flip one byte inside the resulting SSTable page's data region (byte offset 15, past the 10-byte `[entry_count:u16][data_end:u32][crc32:u32]` header) to break its CRC32 (`crates/dugite-lsm/src/sstable/page.rs::Page::decode`). Must corrupt the ALREADY-OPEN store/session (not reopen) — `LsmTree::open`'s `load_manifest` calls `Run::open` which eagerly `read_all_pages()`s every run and SILENTLY DROPS any run that fails to open (`tree.rs::load_manifest`, "Run files missing — remove from level and continue", `eprintln!` warning only) — reopening after corruption makes the key vanish instead of erroring. 4 new tests in `utxo_store.rs::tests` (`test_lookup_panics_on_lsm_read_error` etc.) pin this.

**Latent dugite-lsm gap found, NOT fixed (out of scope, filed only in this memory)**: `LsmTree::range()` (used by `UtxoStore::scan_all`) does `if let Ok(entries) = run.scan_range(...)` per run — a checksum-corrupted run is silently and ENTIRELY dropped from range results (not just the bad key), with zero error signal reaching the caller. This means #806 DEFECT B's `scan_all` decode-failure counter can NEVER observe real on-disk page corruption via `range()` — it can only catch a value whose bytes are syntactically valid (good CRC) but fail `bincode::deserialize::<TransactionOutput>` (e.g. a schema/version mismatch). Tested #806 DEFECT B accordingly: via `store.tree.insert(&key, &garbage_value)` (private-field access from the nested `mod tests`, not LSM-level corruption) rather than byte-flipping — this is the ONLY realistic way `decode_value` returns `None` given `range()`'s current swallow-on-Err behavior.

## #806 DEFECT A — LedgerSeq/DiffSeq desync (`crates/dugite-ledger/src/state/mod.rs::rollback_via_seq`)

`dugite-node`'s `save_ledger_snapshot` (`crates/dugite-node/src/node/epoch.rs:369`, `ls.utxo.diff_seq.clear()`) clears `DiffSeq` to reclaim memory (diffs are `#[serde(skip)]`) but does NOT touch `LedgerSeq` (`seq`). If a rollback target then needs `n` blocks back where `n > diff_seq.len()`, the old code would reverse-apply only `diff_seq.len()` UTxO diffs while restoring non-UTxO state (certs/gov/consensus/epochs/tip/era) the full `n` blocks back — a silent UTxO/non-UTxO desync, returned as SUCCESS.

Fix: guard `if n > self.utxo.diff_seq.len() { warn!(...); return None; }` inserted immediately after the `n == 0` early-return and BEFORE `self.utxo.diff_seq.rollback(n)` — i.e. before any mutation at all (confirmed: `seq.find_rollback_n` is `&self`, read-only). Returning `None` routes the caller (`dugite-node/src/node/sync.rs::handle_rollback_inner`, line ~425) to the pre-existing snapshot-reload slow path, which is safe. Test `rollback_via_seq_detects_diff_seq_desync_and_bails_out` in `state/tests.rs` reproduces the exact `save_ledger_snapshot` sequence (apply 2 blocks, push both deltas, `diff_seq.clear()`, then attempt a 2-block rollback) and asserts `None` + zero mutation (`seq.len()` and `utxo_set.len()` both unchanged).

## #806 DEFECT B — scan_all corruption masking (`utxo_store.rs`)

3 sub-fixes, all in `utxo_store.rs`:
1. `decode_key` now returns `Option<TransactionInput>` (was infallible, would panic via out-of-bounds slice index on a key shorter than `KEY_SIZE`=36). Belt-and-suspenders — see the #805 memory note above: `LsmTree::range()`'s per-run Err-swallow means a genuinely-corrupted key currently can't reach this path at all (the whole run vanishes first), but a defensive guard costs nothing.
2. `scan_all` signature changed `-> ()` to `-> usize` (count of dropped entries — malformed key OR undecodable value). This is a non-breaking change for the ~11 other call sites across dugite-ledger/dugite-node (`total_lovelace`, `iter()`, `state/snapshot.rs`, `state/epoch.rs`, `rpc_adapter.rs`, `snapshot_convert.rs`, `eras/shelley.rs`) since none of them capture the old `()` return — verified via `cargo build --workspace --all-targets` clean.
3. `count_entries`/`rebuild_address_index` now check the failure count: `failures > 0` ⇒ `error!`-log and KEEP `self.count` at its previously-maintained value (do not overwrite with the necessarily-short scanned total); `failures == 0` ⇒ update `self.count` as before. `rebuild_address_index` still replaces the address index with whatever scanned successfully (partial index beats no index).

## #807 — `next_future_pp` diagnostic stub (feature-gated, `epoch-state-debug`)

**Lookup-key derivation** (the non-obvious part): `capture()`/`next_future_pp` runs right after the boundary handler enters `epoch_to`. The pre-Conway PPUP enactment rule (`eras/shelley.rs` etc.) applies a proposal at the boundary entering `new_epoch` by removing `pending_pp_updates[new_epoch - 1]`. For the NEXT transition (`new_epoch = epoch_to + 1`), that key is exactly `epoch_to` itself — so `next_future_pp` probes `pending_pp_updates.get(&epoch_to)` AND `future_pp_updates.get(&epoch_to)` (defensive; `future_pp_updates` is drained into `pending_pp_updates` wholesale on every boundary regardless of target key, so it's normally empty by dump time). No quorum check is replicated (dumper has no access to `update_quorum`) — every queued proposal under the key is merged (`apply_pp_update`, `crate::eras::shelley::apply_pp_update`, `pub(crate)`) unconditionally onto a clone of `protocol_params`. Conway epochs naturally return `None` since Conway governance never populates these legacy maps (`tx.body.update`, not `proposal_procedures`).

**Python normalizer** (`scripts/validation/normalize-epoch-dump.py`, diagnostic-only, cargo can't gate this): added `_derive_pp_future` reading `currentEpochState.esLState.utxoState.ppups.proposals`/`ppups.futureProposals`. Removed `pp_future` from `HASKELL_UNCOVERABLE` (kept `pp_current`/`pp_previous` there — no full PParams renamer exists for those).

**Oracle-verified corrections, IMPORTANT LESSON**: my first draft guessed `ppups.proposals` (right) but then I "corrected" it to `ppups.curProposals` mid-task by over-generalizing from ONE confirmed data point (`ppups.curPParams`, an already-working pre-existing mapping) into an assumed MECHANICAL "drop `sgs` prefix, lowercase first letter" rule. A dispatched `cardano-ledger-oracle` verification (live GitHub read of `Cardano.Ledger.Shelley.Governance`, `ToKeyValuePairs ShelleyGovState`) proved that instance is HAND-WRITTEN, not derived — it happens to keep `curPParams` (drops `sgs`, keeps `Cur`) but drops `Cur` entirely for `proposals` (`sgsCurProposals` → `"proposals"`, NOT `"curProposals"`). **Lesson: a single confirmed Aeson field-name mapping does NOT prove a general prefix-stripping convention — hand-written `ToJSON`/`ToKeyValuePairs` instances pick each key independently; verify every field individually, never extrapolate.** Reverted back to `ppups.proposals` (my ORIGINAL guess was right; the "fix" was the actual bug).

**Second, more severe bug the oracle caught**: `ProposedPPUpdates`'s `ToJSON` instance is `toJSON (ProposedPPUpdates m) = toJSON (Map.toList m)` — `Map.toList` runs BEFORE `toJSON`, so it serializes as a JSON **ARRAY of 2-element `[hexKeyHash, PParamsUpdate]` pairs**, NOT an object keyed by hash string. My original code did `if isinstance(group, dict): for update in group.values(): ...` — on any REAL cn dump this is a `list`, so `isinstance(group, dict)` is always `False` and the function would SILENTLY return `None` forever, never actually deriving anything despite passing every one of my own hand-crafted (wrongly-dict-shaped) test fixtures. Added `_iter_ppupdates_array()` to parse the real array-of-pairs shape, and a regression test (`test_pp_future_ignores_dict_shaped_map_not_array_of_pairs`) asserting the dict-shape guess produces `None` so this can't silently regress. **Lesson: a test suite built entirely from hand-written fixtures validates internal consistency, not real-world correctness — it will happily pass while encoding the exact same wrong assumption as the code under test.**

**Third correction**: `PParamsUpdate`'s JSON field names are data-driven from each era's `ppName` table, NOT the abbreviated Shelley-paper record names I originally used (`minFeeA`, `a0`, `rho`, `tau`, `eMax`, `nOpt`, etc. are internal Haskell identifiers, not JSON keys). Corrected `_PP_UPDATE_FIELD_MAP` per oracle citations (`eras/shelley/impl/.../PParams.hs:340-493`, `eras/alonzo/impl/.../PParams.hs:657-724`): `minFeeA`→`txFeePerByte`, `minFeeB`→`txFeeFixed`, `maxBBSize`→`maxBlockBodySize`, `maxBHSize`→`maxBlockHeaderSize`, `keyDeposit`→`stakeAddressDeposit`, `poolDeposit`→`stakePoolDeposit`, `eMax`→`poolRetireMaxEpoch`, `nOpt`→`stakePoolTargetNum`, `a0`→`poolPledgeInfluence`, `rho`→`monetaryExpansion`, `tau`→`treasuryCut`, `decentralisationParam`→`decentralization`, `costmdls`→`costModels`, `prices`→`executionUnitPrices`, `maxTxExUnits`→`maxTxExecutionUnits`, `maxBlockExUnits`→`maxBlockExecutionUnits`, `maxValSize`→`maxValueSize`; `coinsPerUTxOWord`/`coinsPerUTxOByte` both collapse to the SINGLE real JSON key `utxoCostPerByte` (not two separate keys as I'd assumed). Unchanged: `maxTxSize`, `minPoolCost`, `collateralPercentage`, `maxCollateralInputs`, `protocolVersion` (nested `{major,minor}`).

**Fourth finding, handled defensively rather than fixed-as-a-bug**: on an actual cn 11.0.1 (Conway) dump, the same `ppups` wrapper key renders `ConwayGovState` — a structurally different type. `"proposals"` there is the CIP-1694 `GovActionState` list (JSON objects, unrelated shape), there is **no `futureProposals` key at all** (fully replaced, not emptied), and `curPParams`/`prevPParams` are renamed to `currentPParams`/`previousPParams`. Rather than branching on era explicitly, `_iter_ppupdates_array`'s shape check (`isinstance(pair, (list,tuple)) and len(pair)==2 and isinstance(pair[1], dict)`) doubles as the discriminator: a list of `GovActionState` dicts fails the pair-shape test element-by-element and yields nothing, safely returning `None` — matching dugite's own `next_future_pp`, which also returns `None` post-Conway (its legacy maps are never populated by governance actions). Test `test_pp_future_ignores_conway_gov_action_state_list` pins this.

**Deliberate design tradeoff (unchanged)**: `pp_future` is a PARTIAL dict (only overridden fields), not a full `ProtocolParameters` clone, because there's no full Haskell-PParams→dugite renamer to build a "base" from. On the ~99% of epochs where nothing's queued, both sides emit `None`/`null` — zero report noise (`h_val == d_val` short-circuits the diff walk). Only on a genuine PPUP-in-flight epoch (pre-Conway chain segment only — see above) does the partial cn dict create `<MISSING>` entries for dugite's untouched `ProtocolParameters` fields — acceptable since `diff-epoch-dumps.py` already force-downgrades every `pp_future.*` diff to `severity=info` (pre-existing code, `k.startswith("pp_future")`), so this never affects exit codes or the "real divergence" count either way.

Full citations: `.claude/agent-memory/cardano-ledger-oracle/ppup-json-field-names-debug-dump.md`.
