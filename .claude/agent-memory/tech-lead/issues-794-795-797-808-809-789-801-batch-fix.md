Batch of 7 independently-verified dugite-ledger fixes landed together on
`fix/ledger-review-2026-07-04` (uncommitted, left for user to review/commit).
All gates green: 1618/1618 tests pass, clippy clean, fmt clean, full
workspace build clean.

- **#794** (`eras/common.rs::validate_block_ex_units`): removed the
  `if tx.is_valid` guard — Haskell's `foldMap totExUnits txs` (Bbody.hs) has
  no IsValid filter; an invalid tx still carries redeemers that count toward
  the block ExUnits budget. Made dugite STRICTER (closes an over-accept).
- **#795** (`state/apply.rs`, two sites ~596 Byron + ~1065 Shelley+): a
  duplicate tx hash within a block is now block-fatal in `ValidateAll` mode
  only (`BadInputsUTxO: duplicate transaction hash in block`); `ApplyOnly`
  keeps the old warn+skip for replay tolerance. Both sites gated on
  `mode == BlockValidationMode::ValidateAll` before the existing warn.
- **#797** (`eras/shelley.rs::on_era_transition`, Byron→Shelley branch):
  added `utxo.epoch_fees = Lovelace(0);` right after
  `recompute_shelley_initial_reserves`. **cardano-ledger-oracle CONFIRMED**
  (fresh source fetch 2026-07-06, not from stale memory) that Haskell
  `translateToShelleyLedgerStateFromUtxo` (ByronTranslation.hs:103-181)
  constructs `utxosFees = Coin 0` and `esSnapshots = emptySnapShots` (ssFee=0)
  — Byron never had a fee-pot accumulator; the burn is entirely implicit in
  `reserves = maxSupply - sumCoinUTxO(liveUTxO)`. Without the zero, ValidateAll
  (accumulates real implicit Byron fee) and ApplyOnly (accumulates
  `tx.body.fee.0`, always 0 for decoded Byron txs) permanently diverge at the
  fork — same class as #763. See
  `.claude/agent-memory/cardano-ledger-oracle/byron-duplicate-inputs-and-shelley-translation.md`
  for the full oracle citation.
- **#808** (`state/apply.rs` `pool_block_increment` delta): replaced the
  inline first-slot-of-epoch formula (which omitted `- shelley_transition_epoch`)
  with the canonical `crate::eras::common::first_slot_of_shelley_epoch` helper.
  Verified the test actually catches the regression by reverting and
  confirming failure (`left: None, right: Some(pool_id)` at mainnet-shaped
  epoch 210 / d=1/10 numbers) before re-applying.
- **#809** (u64 saturating_add hygiene): `conway.rs:786`, `shelley.rs:572`,
  `apply.rs` fees_collected fold, `utxo.rs::total_lovelace` all switched to
  `saturating_add`. `utxo.rs::insert` address_index push now guarded with
  `.contains(&input)` to prevent duplicate index entries on TxIn re-insert.
  `utxo_store.rs` deliberately left untouched (already correct/reference).
- **#789 + #801** (`validation/collateral.rs::check_collateral`, folded
  together — same function, same effective_collateral variable): (a) `qty > 0`
  → `qty != 0` in the net-token check so a NEGATIVE residual (over-declared
  `collateral_return` token) also flags `CollateralHasTokens`, matching
  Haskell `isAdaOnly = Map.null`; (b) `effective_collateral` changed from
  `u64` (via `saturating_sub`, which clamped negative balances to 0) to a
  signed `i128` that preserves sign; (c) the `body.fee.0 * collateral_percentage`
  unchecked u64 multiply replaced with the i128 form
  `100*effective_collateral < collateral_percentage*fee` — the exact integer
  equivalent of `effective_collateral < ceil(fee*pct/100)` (proved via the
  standard identity `a >= ceil(b/c) iff a*c >= b` for c>0), verified against
  all 3 existing proptests (`collateral_sufficient_no_error`,
  `collateral_insufficient_rejected`, `prop_collateral_utxo_invariant`) still
  passing byte-for-byte.
  **Deliberate deviation from the issue's "recommended" fix**: kept
  `ValidationError::CollateralMismatch.computed` as `u64` (via
  `effective_collateral.max(0) as u64`) rather than widening to `i128` as the
  issue suggested — widening would ripple into `dugite-network`'s
  `TxValidationError::CollateralMismatch` (wire type, N2C LocalTxSubmission
  tag 20 IncorrectTotalCollateralField encoding) and `dugite-node/serve.rs`'s
  conversion site, neither of which was in the listed fix scope. The `.max(0)`
  clamp is display-only; the actual signed comparison already uses the exact
  i128 value, so no correctness is lost.

**Test-writing pattern that mattered**: for #795 and #808, I verified the new
tests actually catch the bug by temporarily reverting the fix and confirming
the test fails with the expected wrong value, then re-applying — cheap
insurance against a test that "passes but doesn't test anything" (e.g. if an
earlier block-level check like `validate_block_body` short-circuits before
the code path under test is ever reached). Worth doing for any test in
`apply_block_impl`/`apply_block_with_delta` given how many block-fatal checks
run before the per-tx loop.
