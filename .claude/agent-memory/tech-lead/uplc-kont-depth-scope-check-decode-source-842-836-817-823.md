Implemented 4 verified dugite-uplc decode/machine-strictness fixes: #817 (CEK continuation-depth cap removal), #823 (eager checkScope pass), #836 (decode_script_bytes heuristic replacement), #842 (read_natural_u64 overflow guard). 999/999 UPLC conformance corpus stayed byte-identical throughout; full workspace nextest (7275 tests) green.

## #817 — MAX_KONTINUATION_DEPTH removed
`crates/dugite-uplc/src/machine/context.rs` `Kont::push` made infallible (dropped `Result`); `MAX_KONTINUATION_DEPTH` const deleted from `mod.rs`; `?` removed from the 7 `kont.push(...)` call sites in `step.rs`. Haskell's CEK `Context` has no depth field — ExBudget is the only bound, and `Kont` is a heap `Vec<Frame>` (no OS-stack recursion), so removing the cap is stack-safe. Regression test: 5000-deep non-tail `addInteger` chain (`(addInteger 1 (addInteger 1 (...)))`) now succeeds where it used to hit the 4096 cap. Did NOT touch the flat decoder's separate `FLAT_MAX_DEPTH` (sibling, different concern — decode-time term-tree depth vs machine continuation-stack depth).

## #823 — eager checkScope pass
New module `crates/dugite-uplc/src/scope_check.rs`. Mirrors Haskell's `UntypedPlutusCore.Check.Scope.checkScope` EXACTLY including its blind spot: recurses through `Var`/`Lam`/`App`/`Force`/`Delay` only — **does NOT recurse into `Constr` args or `Case` (scrutinee or branches)**. A fully-recursive check would over-reject mainnet-valid scripts with "free"-looking indices inside unreached Constr/Case subtrees. Wired into `eval_redeemer::eval_resolved_redeemer` right after the fully-applied term is built, before `evaluate_with_budget` — this is the SOLE production entry point that builds a `PhaseTwoError`-typed pipeline (the UPLC conformance harness calls `evaluate_with_budget` directly and does NOT go through this check, which is why the 999-corpus is unaffected). New `UplcError::FreeVariable(u64)` variant, classified as `PhaseTwoError::ScriptEvaluationFailed` (script failure / is_valid=false path), NOT `Internal`. Uses `stacker::maybe_grow` per recursive call (mirrors `flat::term::validate_term_depth`'s pattern) since a #817-shaped 5000-deep script must not blow the Rust call stack during this eager pre-check either.

## #842 — read_natural_u64 word64 overflow
`crates/dugite-uplc/src/flat/bits.rs`: split into `read_natural_u64` (unchanged, lenient — silently truncates at shift=63 if chunk>1) and new `read_word64_strict` (rejects when `shift==63 && chunk>1`, matching Haskell `dWord64`'s `countLeadingZeros w < 63` rule exactly). Both share a private `read_natural_u64_impl(strict: bool)`. Applied `read_word64_strict` ONLY at the two genuinely-Word64-typed sites: De Bruijn `Var` index decode and `Constr` tag decode (both in `flat/term.rs`). Deliberately did NOT touch `program.rs`'s version-triple decode (`read_natural_u64` stays lenient there) — Haskell types Version's 3 fields as unbounded `Natural`, which never rejects; capping it would make dugite STRICTER than Haskell, a different bug. Test proves a value at the u64::MAX boundary is NOT rejected for the version triple.

## #836 — decode_script_bytes heuristic: CRITICAL correction mid-task
**Original verdict** (oracle-informed, high confidence) said: delete the first-byte heuristic, make `decode_script_bytes_uncached` unconditionally `Program::from_cbor(bytes)` for ALL script sources (witness AND reference).

**I initially "corrected" this** based on an in-repo comment from the already-committed #792 fix (`crates/dugite-ledger/src/validation/scripts.rs`, commit `f733baa5a9`), which claims reference scripts (`ScriptRef::PlutusVN`) are "already singly-unwrapped raw flat... no further CBOR wrapper to strip", vs witness scripts needing `from_cbor`. I implemented a `ScriptSource` enum (`Witness`/`Reference`) threaded through `ResolvedRedeemer`/`find_script_bytes`/the decode cache, dispatching `from_cbor` for Witness and `from_flat` for Reference.

**This broke a REAL captured on-chain fixture** (`tests/fixtures/phase2_onchain/tx6.json`, `onchain_babbage_scripts_validate_within_declared_budget`) with `filler missing terminating 1 bit within 8 bits`. Root-caused by writing a throwaway decode-dump test against tx6.json's actual reference-script bytes (as produced by `dugite_serialization::decode_transaction_output`'s `read_script_ref`): the bytes start with `0x59 <2-byte-len>` (a genuine CBOR bytestring header) whose declared length + header size exactly equals the total slice length, and stripping it reveals `01 00 00 32 32...` — an exact flat version-triple `(1,0,0)` + term bits. `Program::from_cbor` succeeds, `Program::from_flat` fails, on the RAW (unstripped) bytes.

**Scanned every real fixture with witness scripts too** (`tx0/tx1/zero_asset_tx0/zero_asset_tx1/zero_asset_invalid_tx4/tx_v3_spend_71579b77.json`): every single witness script sample is ALSO `from_cbor`-only (CBOR-double-wrapped), consistent with #792's witness-side claim but contradicting its reference-side claim.

**Conclusion**: the #792 comment's reference-script claim is empirically WRONG — likely written against a hand-rolled/synthetic `dugite-serialization` round-trip test (`era_conway.rs`'s script_ref tests encode+decode via the SAME assumption, so they self-confirm without ever exercising real on-chain byte shapes) rather than real captured chain data. **Both witness AND reference scripts are CBOR-bytestring-double-wrapped on the actual wire; `decode_script_bytes_uncached` must be unconditionally `Program::from_cbor(bytes)` for both, exactly as the original oracle verdict said.**

**Reverted** the entire `ScriptSource` plumbing (enum, `ResolvedRedeemer` field, `find_script_bytes` 3-tuple return, decode-cache key, 7 call sites in `redeemer_resolve.rs`) back to the simple original shape, with `decode_script_bytes_uncached` = unconditional `from_cbor`. Kept the test-fixture fix (the 2 uplc unit-test helpers `smoke_v3_unit_script_runs_and_returns_unit` / `minimal_v3_setup` now pass CBOR-wrapped `script_cbor` directly instead of manually-unwrapped `inner` flat bytes) since that part was independently correct regardless of the Witness/Reference question.

## Outstanding P0/P1 finding — NOT fixed in this session (out of declared scope)
`crates/dugite-ledger/src/validation/scripts.rs`'s `plutus_ref_script_decodes` (from #792, commit `f733baa5a9`) calls `Program::from_flat(bytes)` ONLY on reference-script bytes. Per the empirical evidence above, this is almost certainly WRONG for real on-chain reference scripts and would cause `check_malformed_reference_scripts` to FALSE-REJECT every legitimate Babbage/Conway tx that outputs a UTxO carrying a genuine Plutus reference script (`MalformedReferenceScripts` false positive) — a consensus-relevant over-rejection (dugite rejects blocks/txs cardano-node accepts). This needs its own dedicated fix + oracle verification pass in dugite-ledger (`plutus_ref_script_decodes` should likely become `Program::from_cbor` too, matching `plutus_witness_script_decodes`), plus fixing whatever synthetic test in `era_conway.rs`/`era_babbage.rs` baked in the wrong assumption. Flagged for the user/dugite-ledger owner; verify against `cardano-ledger-oracle` before changing.

## Lesson
An in-repo comment describing a "verified" wire-format split (even one attached to a previous commit with a plausible-sounding rationale) is a CLAIM, not ground truth — always cross-check against REAL captured on-chain fixture bytes (this project's own `tests/fixtures/phase2_onchain/*.json`) before trusting it, especially for anything CBOR-wrapping-related. A synthetic round-trip test that encodes-then-decodes via the same assumption cannot catch a wrong assumption; only real chain data can.
