On 2026-07-06 the user (Michael) asked for an oracle-verified audit of 4 specific dugite behaviors against cardano-ledger/plutus-ledger-api Haskell source, explicitly stating he would only change dugite's code where a genuine divergence is confirmed (not "fix" already-correct code). Full source citations live in [[plutus-txinfo-translation-v3unit-byron-pointer]] (Q1/Q3/Q4) and [[bounded-ratio-decode-and-enact-totality]] fact 4 (Q2).

**Why**: dugite is auditing PlutusV3/ScriptContext-translation exactness ahead of further Conway governance/Plutus conformance work; this was a precision check, not a bug report — the user had specific hypotheses to confirm/refute rather than an observed failure.

## Results

1. **Q1 (PlutusV3 unit-return check) — dugite is CORRECT, no change needed.** Haskell's `processLogsAndErrors` (`plutus-ledger-api/src/PlutusLedgerApi/Common/Eval.hs`) enforces `InvalidReturnValue` for any ledger-language other than V1/V2 — gated by language identity (`ll`), not by protocol version, and applies unconditionally at every PV where V3 exists (PV9+, live since before Chang#1 mainnet activation, plutus commit `d34e4d3f`). dugite's `crates/dugite-uplc/src/eval_redeemer.rs:300-310` already does exactly this.

2. **Q2 (rational reduction) — CONFIRMED DIVERGENCE, not yet fixed.** Haskell's `%` (GHC `Data.Ratio`) unconditionally reduces every decoded `Rational`/`BoundedRatio` to lowest terms at CBOR-decode time (`decodeIntegralRational`, `decodeRationalWithoutTag`, etc. — no code path preserves an unreduced wire pair). dugite's `crates/dugite-serialization/src/decode/reader.rs::read_rational` and `dugite_primitives::transaction::Rational` (`crates/dugite-primitives/src/transaction.rs:352`) never reduce; `crates/dugite-uplc/src/populate_gov.rs::rat()` emits the raw stored numerator/denominator into `ChangedParameters` Plutus Data verbatim. Only matters for non-canonical (but validly-decodable) on-chain rationals reaching a V3 script's `ScriptContext` via a `ParameterChange` governance action — threshold comparisons elsewhere are reduction-invariant (cross-multiplication) and unaffected. **Not yet filed as a GitHub issue or fixed** as of 2026-07-06; fix = gcd-reduce at `read_rational` decode time.

3. **Q3 (Byron address in TxInfo, Alonzo vs Babbage+) — CONFIRMED DIVERGENCE, not yet fixed.** Haskell: Alonzo-era `EraPlutusTxInfo 'PlutusV1 AlonzoEra` silently drops Byron-addressed inputs/outputs (`catMaybes`/`mapMaybe` over `Maybe`, explicit source comment calling it "a mistake" that must be preserved); Babbage-era (and Conway, which reuses Babbage's functions unchanged) hard-errors via `ByronTxOutInContext` for the identical `PlutusV1` language — the dispatch key is the ERA type parameter, not the language tag. dugite's `crates/dugite-uplc/src/tx_info_populate.rs::address_to_plutus` hard-errors unconditionally for every era (used by both `populate_tx_info_v1`/`populate_tx_info_v2` in `crates/dugite-uplc/src/populate_v1_v2.rs`, with no era parameter threaded in at all), so it's applying Babbage+'s strict behavior even to a hypothetical Alonzo-era transaction. **Not yet filed as a GitHub issue or fixed** as of 2026-07-06; fix requires threading era into the V1 TxInfo builder path and doing list-level filtering only for the Alonzo case. Low real-world urgency: mainnet's Alonzo window closed at the Vasil HF (epoch 365, Sept 2022) and preview/preprod (dugite's current soak targets per [[project_epoch_diff_harness_2026_05_22]]-style work) may have little-to-no live Alonzo-era Byron-address+Plutus-V1 traffic left to replay — worth fixing for completeness/ledger-rules ImpSpec conformance, not urgent for live soak parity.

4. **Q4 (StakingPtr translation across eras, esp. Conway) — dugite is CORRECT, no change needed.** `transAddr`/`transStakeReference` live in ONE shared module (`libs/cardano-ledger-core/src/Cardano/Ledger/Plutus/TxInfo.hs`) reused verbatim by Alonzo, Babbage, and Conway (Conway's own `TxInfo.hs` doesn't even mention `transAddr`/`StakingPtr` — it calls `Babbage.transTxOutV2` directly). Conway's removal of pointer-address *creation*/DState-resolution is a DELEG-rule/state-layer change, unrelated to this translation function; pre-existing pointer-addressed UTxOs still translate to `StakingPtr{slot,txIx,certIx}` verbatim in Conway. dugite's `crates/dugite-uplc/src/tx_info_populate.rs::pointer_to_plutus` already does this unconditional passthrough correctly.
